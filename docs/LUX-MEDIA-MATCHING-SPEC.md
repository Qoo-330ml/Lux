# Lux 视频媒体后台识别匹配与元数据管理设计规范 (Lux Media Matching & Admin Specification)

> **文档状态**：草案 / 待评审  
> **目标**：规范 Lux 管理员控制台中的**媒体识别匹配（Identification）、重新识别（Re-identify）、元数据锁定（Metadata Locking）与 NFO/图片回写监控**的前后端交互与界面设计。

---

## 1. 识别匹配核心流程与状态机

在 Lux 中，媒体文件扫描后不会强制“粗暴匹配”，而是依据置信度进入不同状态。

### 1.1 媒体条目识别状态 (Identification Status)

| 状态 (Status) | 描述 | 后端触发逻辑 | 前端展示与操作 |
| :--- | :--- | :--- | :--- |
| `LOCAL_CONFIRMED` | **本地确认** | 读取到合法 NFO 或明确的 Provider ID (TMDb ID) | 显示绿标 `[本地 NFO]`，无需人工干预 |
| `ONLINE_CONFIRMED` | **在线匹配确认** | TMDb 自动匹配置信度达到高阈值（标题一致+年份差≤1年） | 显示蓝标 `[TMDb 自动匹配]`，支持重新识别 |
| `PENDING` | **待处理 / 待人工识别** | 无 NFO 且自动搜索无高置信度候选，或有多个极接近候选 | 显示黄标 `[待识别]`，**突出在管理员控制台待处理队列中** |
| `FAILED` | **识别/刮削失败** | TMDb 网络请求超时、TMDb 返回 404 或解析失败 | 显示红标 `[识别失败]`，支持手动重试 |

## 2. 后台匹配核心功能与 UI/UX 界面设计

3. **安全锁定保护**：突出显示已锁定的字段，确保用户手工修改的内容不会被覆写。

### 2.5 NFO 与图片磁盘回写监控 (NFO Writeback Status)

Lux 强调**本地元数据优先与原子回写**。在后台面板中提供回写队列监控：

1. **原子回写机制 (Atomic Writeback)**：写入时使用 `.nfo.tmp` 文件，刷盘确认无误后再原子重命名，防止写入中断损坏原 NFO。
2. **状态提示与日志**：
   - 🟢 `回写成功`：NFO 与 `poster.jpg` / `fanart.jpg` 已保存至 NAS 媒体目录。
   - 🔴 `权限不足 / 目录只读`：明确提示 NAS 挂载权限问题，并提供“重新尝试回写”按钮。

## 3. 前后端 API 契约设计 (Lux API v1 Matching Endpoints)

为了支持上述后台匹配功能，前端与 Axum 后端需交互以下 API：

| HTTP 方法 | 接口路径 (Endpoint) | 功能描述 |
| :--- | :--- | :--- |
| `GET` | `/api/v1/admin/metadata/pending` | 获取待处理 / 匹配失败的媒体列表（支持分页） |
| `POST`| `/api/v1/admin/metadata/search` | 根据标题 / 年份 / TMDb ID 实时搜索 TMDb 候选 |
| `POST`| `/api/v1/items/:id/identify` | 选定候选条目，执行识别绑定并回写 NFO |
| `PATCH`| `/api/v1/items/:id/metadata` | 更新媒体字段与锁定状态 (`locked_fields`) |
| `GET` | `/api/v1/items/:id/images/candidates` | 获取 TMDb / 本地海报与背景图候选列表 |
| `POST`| `/api/v1/items/:id/images/select` | 选定并下载海报/背景图回写磁盘 |

---

## 4. 总结与后续动作

通过上述匹配点规范：
1. **解决乱匹配问题**：置信度不够的影片统一进入 `PENDING` 队列，不再盲目搜刮。
2. **高效人工干预**：通过带缩略图与匹配度的搜索弹窗，管理员 2 秒内即可完成手动矫正。
3. **回写与锁定保障**：手工修正的内容自动锁定并原子写回 NAS 本地 NFO，确保重启或重新扫描不丢失数据。
