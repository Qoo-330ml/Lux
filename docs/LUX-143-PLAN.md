# LUX-143：本地元数据优先与全局刮削模式

## 目标

媒体库扫描始终读取本地 NFO 和图片；媒体库的刮削器只表示可选的在线补充来源。新库首次扫描和管理员手动整库匹配默认自动选择高置信度最佳候选，并按媒体库图像策略完成 NFO/图片写回；管理员从全局媒体策略发起批量刮削时，可以选择“仅补全”或“完整刮削”。

## 行为契约

- 未配置刮削器时仍正常读取本地 NFO、图片和技术信息，不发起在线刮削请求。
- “仅补全”只写入缺失的未锁定 NFO 字段和缺失图片。
- “完整刮削”刷新未锁定的 NFO 字段，并替换已有图片；在线没有返回的图片不删除已有本地图片。
- 已锁定的 NFO 字段在两种模式下都不覆盖。
- 全局刮削必须进入持久化后台任务队列，服务重启后继续处理。
- 低置信度或无法完成元数据匹配的条目保留本地内容并进入失败/待处理状态，不自动写入不确定候选。
- 新媒体库首次添加根路径并完成扫描后自动提交 `FILL_MISSING` 匹配任务；媒体库入口的整库“元数据匹配”也使用该自动流程，不要求用户逐条选择候选。

## 接口

- 保留指定条目元数据重新匹配接口的“只搜索并生成候选”语义；媒体库级整库匹配改为自动选择高置信度候选并写回。
- 新增媒体库元数据刷新接口，接收 `{ "mode": "FILL_MISSING" | "FULL_REFRESH" }`，每次媒体库操作返回一个持久化后台任务。
- 一个任务内部以最多 16 路异步 worker 并行处理条目；条目状态、失败重试和 SQLite/NFO 短事务仍保持逐条独立。
- 任务持久化模式，旧任务默认为 `REIDENTIFY`，不破坏已有任务恢复。

## 预计修改范围

- Rust：元数据任务应用服务、候选选择、任务存储与 migration、Lux 管理 API、相关集成测试。
- Web：全局策略模式选择、全局/媒体库刷新入口、API 类型与客户端、相关组件测试。
- 文档：`docs/API.md` 与 `docs/LUX-DEVELOPMENT.md` 的行为和验收说明。

## 边界

- 不新增依赖，不改变 Emby DTO，不在 HTTP 请求中执行扫描、NFO 解析、图片下载或在线请求。
- 图片替换仍使用现有的路径校验、大小限制和原子写回流程。
