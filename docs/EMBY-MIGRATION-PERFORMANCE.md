# Emby 迁移性能记录

本记录覆盖 Emby 迁移的页面写入路径；它用于防止批量写入、游标提交和报告写入退化为逐条事务，不能代替真实 Emby/NAS 压测。

## 合成页基准（2026-08-29）

执行命令：

```bash
cargo test --locked --lib migration_page_batch_benchmark_records_operation_counts -- --ignored --nocapture
```

运行环境：macOS，`aarch64`（本机 ARM64），SQLite 临时数据库。该结果**不可外推为 NAS/x86 性能**。

| 指标 | 结果 |
| --- | ---: |
| 页面大小 / 有效条目 | 500 / 500 |
| 匹配 / 跳过 | 500 / 0 |
| 模拟来源 RPC | 1 |
| 重试产生的重复来源请求 | 0 |
| 数据库语句 | 17 |
| 数据库事务 | 1 |
| 耗时 | 7 ms |
| 吞吐 | 65,444 items/s |
| 进程峰值 RSS | 23,166,976 bytes |

每 500 个来源条目在一个事务中处理；为保持 SQLite 参数数量受控，条目报告、导入记录和已处理标记各拆为 5 个 100 条的写入批次，另有用户状态和游标/计数更新。实际迁移会在完成时以结构化日志记录来源 RPC 数、事务数、最大页面条目数、处理/匹配/跳过/失败数及总耗时，且不会记录来源 URL、API key 或用户密码。

编排层还有四条“按需”路径：新任务依靠当前用户内存去重，不再为每个来源页查询空的已处理表；只有恢复中的用户才启用持久化去重查询，游标损坏或无法映射时会对所有用户保留该保护。选择媒体状态但来源没有任何有效状态条目时，完整媒体身份索引不会加载；选择人物收藏但来源没有有效收藏人物时，人物身份索引也不会加载；Web 第 2 步只在勾选媒体状态或媒体库权限后请求目标媒体库列表。上述路径没有改变 500 条页面批次的 17 条写入语句基准，收益主要体现在空迁移和多页新任务的读取开销。

用户资料同步同样先在内存比较禁用、远程访问和下载权限；目标值已经一致时跳过用户更新事务，避免重复迁移只刷新 `updated_at`。

支持过滤能力的来源插件还会接收已选用户 ID，因此执行阶段不会重新读取完整用户清单；按来源库映射后确认某用户在目标白名单中没有可读源库时，宿主直接跳过该用户的状态 RPC。旧插件不接收这些可选参数，兼容路径仍可能读取更大范围，但目标端写入边界不变。媒体身份候选查询按来源页执行，Provider ID 使用 `media_item_provider_ids` 索引，标题/年份回退受当前页 lookup 数量限制；Provider 唯一命中时跳过标题回退列为下一阶段优化。

目标 Lux 媒体库白名单会进入候选 SQL 的 `library_id` 条件，因此常规命中不会读取白名单外库的完整身份行；若白名单内没有候选，宿主仅对当前页未解析条目做一次无过滤回退，以保留
`TARGET_LIBRARY_EXCLUDED` 诊断报告。多个来源状态筛选页中的重复 Emby 条目会在候选查询前按条目 ID 去重，避免 PLAYED/FAVORITE/RESUMABLE 重复读取同一 Lux 身份。

当同时选择多个媒体状态筛选项时，宿主仍分别调用每个 `stateFilter`，但在每次调用中只投影这些已选筛选项对应字段的并集，再按 Emby 条目 ID 去重；这样不会为未选字段增加来源读取，也不会因同一条媒体跨筛选出现而漏掉已选的收藏、进度或播放信息。

分页循环的取消轮询只读取 `cancel_requested` 标量，不再重复加载迁移任务的完整列集合；任务不存在时仍按未请求取消处理，保持原有恢复语义。

坏页恢复预算为每个逻辑页最多 32 次来源 RPC。预算耗尽后，未恢复范围作为 `PLUGIN_INVALID_RESPONSE_RECOVERY_BUDGET` 诊断记录写入并推进游标；这用有限失败成本换取后续页面继续迁移，避免异常插件造成指数级拆分。

## 本轮新增的低风险优化（2026-08-30）

- 恢复任务在读取 `emby_migration_handled_items` 后，先从当前页移除已经成功提交的条目，再构造 Provider/标题候选查询；重试不会为已处理条目重复读取 Lux 身份。
- 同一来源页内具有相同类型、标题、年份、季集键和 Provider ID 的匹配键只保留一份，减少 SQL OR 条件、绑定参数和重复候选行；条目 ID 级别的去重仍由宿主保留，因此不会改变报告和状态语义。
- 用户阶段先按规范化用户名批量读取已有 Lux 用户，再按需创建缺失用户；正常迁移不再对每个已存在用户发起一次独立用户名查询。dry-run 仍不读取用户表。
- 已显式选择目标库时复用创建任务时完成校验的目标库 ID，不再额外扫描启用库列表；未指定目标库的旧任务仍保留启用库扫描和兼容语义。

用户批量查询按最多 100 个名称一组；因此 100 个已存在用户从最多 100 次用户名查询降为 1 次（超过 100 个时按组数线性增加）。

## 下一阶段优化方案（需项目所有者确认）

按预期收益和风险排序：

1. **Provider 优先候选查询**：当前页候选 SQL 仍会对整页执行 Provider 查询后再执行标题/年份回退，即使 Provider 已唯一命中。先用索引确定唯一 Provider 命中，仅对未命中条目发起标题回退；保持冲突报告和白名单外诊断不变。

2. **来源用户分页/搜索**：扩展 `migration.list_users` 的可选 `startIndex`、`limit`、`search`，配置页只请求当前页；旧插件继续返回完整列表。需要同步更新插件 SDK、协议兼容测试和真实 Emby 插件。
3. **用户链接批量写入**：将用户映射报告按 100 条一批写入单事务；用户创建/资料变更仍逐用户执行，以保留密码占位和最后管理员保护。先增加查询/事务计数基准，再替换逐条 link upsert。
4. **人物候选按页读取**：人物收藏目前首次命中时会加载完整人物身份表；改为按当前页的 Provider/姓名批量查询，并为 provider/name 补齐合适索引，降低大库常驻内存。
5. **有界读写流水线**：在真实 Emby 限流行为和 SQLite 锁等待数据明确后，评估 1 个来源读取窗口 + 1 个数据库写入窗口的双缓冲；并发上限固定且可取消，不使用无限任务或跨任务并发。
6. **可观测性与基准**：记录每阶段来源 RPC 数、候选查询耗时、写入耗时、事务数、最大页大小、跳过原因和峰值内存；提供合成 500/5000/50000 条目基准。所有数字注明硬件、数据库后端和数据集，ARM64 结果不得外推 NAS/x86。

暂不建议：全量 Lux 身份预加载、无限并发、跨用户并行写 SQLite、在用户请求中做完整 dry-run、或为旧插件强行伪造来源端过滤。这些做法会增加内存/锁竞争或破坏兼容边界。

## 当前复测（2026-08-30）

同一合成 500 条页面在本轮代码上复测结果为：17 条数据库语句、1 个事务、7 ms、67,285 items/s、峰值 RSS
23,707,648 bytes（macOS `aarch64`，SQLite 临时库）。该数据集没有重复匹配键，因此主要用于确认新增去重逻辑没有让基线退化；重复键折叠和恢复页跳过已分别由回归测试覆盖。
