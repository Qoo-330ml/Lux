# ADR-020: 采用 PR #10 的首屏性能与扫描生命周期方案

## Status

Accepted

## Date

2026-08-18

## Context

PR #10 同时改进了首页/媒体库首屏查询、Web 端导航后的预取，以及大媒体库扫描任务的
恢复和取消体验。当前 Lux 已经有共享首页缓存，但 PR 基于不同的 migration 序列，且其
扫描锁、失败重试和缓存语义与原规格不同。

## Decision

采用 PR #10 的有效行为，但按当前仓库边界重新实现：

- count/list、媒体详情/集数以及用户状态相关的独立查询可以并行执行。
- 首页和媒体库首屏使用按用户、管理员状态、ACL、筛选和分页隔离的进程内短 TTL 缓存，
  过期时 stale-while-revalidate；缓存读取前仍执行 ACL 校验。
- 扫描锁只覆盖文件系统发现、调和工作项和索引写入；探测、NFO/图片、缩略图、封面和
  在线元数据调度在锁外执行，并使用各自的有界资源配额。
- `PENDING` 扫描取消立即完成；`RUNNING` 扫描在批次边界完成取消并清理工作项。
- 可恢复的失败调和任务保留 checkpoint，在原 job 上重试；历史失败任务没有 checkpoint
  时重建任务。
- 数据库 migration 只从当前最高版本追加。既有 migration 文件名和编号永不重排或重命名。

## Alternatives Considered

### 直接 cherry-pick PR #10

拒绝。PR 的 migration 编号来自不同基线，直接合并会产生 SQLx checksum/版本冲突；同时会
覆盖当前已有的首页共享缓存实现。

### 保留原扫描锁覆盖整个 worker

拒绝。后处理可能包含 NFO、缩略图、封面和在线任务调度，会让其他媒体库在文件扫描已经完成后
仍长期排队，违反扫描期间前台隔离和资源分层目标。

### 只缓存公共首页数据

拒绝作为最终方案。它能降低 ACL 风险，但无法降低继续观看、收藏和推荐等用户首页聚合的重复
计算；改用带用户/ACL 维度的缓存键，并在缓存读取前校验权限。

## Consequences

- 首屏缓存命中速度和扫描期间并发性提升。
- 缓存失效、ACL 变更和用户状态更新需要明确覆盖；缓存 TTL 期间允许短暂返回最近快照。
- 扫描后处理与文件扫描并行后，需要独立的资源配额和测试，防止 CPU/IO 争抢。
- 失败任务会占用可恢复工作项，必须限制队列大小并在重试/取消/完成时清理。
- 所有新索引都必须使用追加 migration，并分别验证 SQLite 和 PostgreSQL 空库迁移。
