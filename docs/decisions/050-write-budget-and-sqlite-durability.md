# ADR-050：写预算与 SQLite 耐久性分级

## 状态

已接受（2026-10-28）。落实 `docs/LUX-DATA-PATH-PLAN.md` 的 W4。

## 日期

2026-10-28

## 背景

扫描与元数据补全会以每秒数百到数千行的速度写 `media_items`，而这些写入原先还要在同一个事务里维护
FTS 索引（含别名 `group_concat` 子查询）。方案评估过引入全局 `WriteCoordinator`，但它会带来优先级
反转与死锁风险，已降级为“写预算 + 队列”。

## 决策

1. **触发器只入队**：`media_items`/`item_aliases` 的搜索类触发器把事件追加到 `catalog_outbox`，
   不再在写事务里维护 `media_search`；消费者 `search_reindex@1` 每批 500 条、1 s 一拍批量重建。
   搜索请求前再做一次有界排空（≤200 条），保证“刚写完就能搜到”。
2. **不引入全局写协调器**：单扫描 writer + 元数据写锁的组合已经足够；新增全局协调器会引入跨子系统
   优先级反转。
3. **消费者预算**：每拍固定批量 + 队列排空后按 2,000 条一批裁剪 outbox；后台消费者不与请求路径共享
   线程池预算（请求路径只做有界排空）。
4. **SQLite 派生写池 `synchronous=NORMAL` 不采纳**：同夹具 6,000 条重建按 500 一批，
   `synchronous=FULL` 187 ms vs `NORMAL` 199 ms（3 次最优，差异在噪声内）。批量提交已把 fsync 次数压到
   12 次/6k 行，独立池只会带来两池同库的锁竞争和“运行中禁止 schema 变更”的运维约束。
5. **provider 索引保持同步**：`media_item_provider_ids` 被合并、归档、库删除与 provider 过滤在同一流程内
   直接读取，异步化会产生“刚写完元数据就做合并判定”读到旧行的窗口；实测其成本为 +2.8 µs/行
   （FTS 是 +18 µs/行）。
6. **持久性等级只按数据类别划分**：权威数据用默认（FULL）；派生数据允许在批量提交里以更低频的提交
   换取吞吐，但不得改变“派生数据可重建”的前提（ADR-048）。

## 后果

- 6,000 文件整库扫描：墙钟 0.42 → **0.37 s**，WAL 11.5 → **11.0 MiB**，FTS 行数一致，队列排空归零；
  满足 W4 验收（墙钟 +≤5%、WAL +≤10%）。
- 5,000 次标题更新的 SQL 级对比：触发器开销 89 → **13 ms**，单条 WAL 2.0 → 0.08 KiB。
- 一致性由三条保证：drain 幂等（失败不推进水位）、队列缺口全量重建、删除时清理 rowid 映射。
  故障注入目前只有单测覆盖，尚无脚本化断电演练（已记录为剩余项）。
