# ADR-015：规范人物身份与共享图片资源

## 状态

Accepted

## 背景

演员出演关系不一定有 TMDb ID。演员可能来自本地 NFO、TMDb、IMDb、豆瓣或未来的其他刮削器。当前
人物关系把 `provider + id` 直接当作人物资源身份，会导致同一演员在不同 provider 下重复创建人物目录和
图片；当前本地 NFO 解析也会丢弃没有 TMDb ID 的演员。

## 决策

将人物系统拆成三层：

1. 出演关系：保存姓名、角色和排序。没有稳定 ID 也必须能够展示。
2. Provider 身份：使用 `provider:id` 表示来源身份，例如 `tmdb:124`、`imdb:nm123` 或
   `douban:123`。
3. 规范人物：使用 Lux 自己分配、不可复用的 `lux-000001` 作为人物资源主键。多个已确认的 provider
   身份可以指向同一个规范人物；新增 provider 身份不能改变该 Lux 编号。

规范人物资源保存人物 NFO 和 Emby 风格的 `folder.<ext>` 图片。多个已确认的 provider 身份共用同一个
规范人物目录；目录已有头像时，后续 provider 不替换或新增头像。人物 NFO 按字段补充，已有非空字段不被
覆盖。没有稳定身份的演员只写入出演关系，不创建人物目录、不发起人物图片下载，并由 Web 显示占位图。

跨 provider 解析由后台任务执行。明确交叉身份、已存在的 provider 映射，以及同一媒体条目中无冲突的一一对应
关系可以自动确认；完整生日只作为辅助证据，姓名或不完整生日不能单独触发合并。低置信度结果进入持久待处理
队列，并保留匹配证据、撤销和拆分记录。旧版 provider 目录、旧 `people.json`、已有 `people/assets` 文件和
旧图片路由保持兼容读取；新图片不再写入 `people/assets`。

配置卷是数据库重建所需的恢复来源：每个人物目录保存版本化 `person.json`，媒体条目快照保存 Lux 人物编号
和稳定媒体来源键。数据库只保存运行时索引；数据库清空后由后台恢复任务按快照重建人物身份和出演关系，不能在
用户请求路径扫描 metadata 目录。

## 备选方案

### 继续使用 provider + id 作为人物主键

实现简单，但 TMDb、IMDb 和豆瓣会为同一人物创建重复目录和图片，无法满足跨来源复用。

### 仅按规范化姓名合并

可以减少目录数量，但同名演员会被错误合并，且姓名可能随语言或译名变化。风险不可接受。

### 新增人物数据库关系表

关系能力更强，但规范人物和 provider 身份的数据库表只作为运行时索引；配置卷中的 `person.json`、provider
索引和媒体关系快照仍是数据库清空后的恢复来源。数据库 schema 必须支持从空数据库迁移，并允许恢复任务幂等重建。

## 后果

- `people.json` 需要版本化并允许没有身份的出演关系。
- `person.json` 需要版本化、校验和原子写入，并保存 Lux 编号、provider 身份、别名、字段来源和锁定状态。
- 详情 API 必须保持无图片演员可见，并对旧版 `id` 字段保持兼容。
- provider 身份索引、规范人物资源和图片资源需要原子写入与路径安全校验；同一 provider 身份只能归属一个 Lux 人物。
- 自动合并必须可审计、可撤销；无法仅凭姓名保证所有 provider 都自动合并，歧义结果仍需管理员处理。
