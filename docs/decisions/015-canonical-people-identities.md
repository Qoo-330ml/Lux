# ADR-015：规范人物身份与共享图片资源

## 状态

Accepted

## 背景

演员出演关系不一定有 TMDb ID。演员可能来自本地 NFO、TMDb、IMDb、豆瓣或未来的其他刮削器。当前
人物关系把 `provider + id` 直接当作人物资源身份，会导致同一演员在不同 provider 下重复创建人物目录和
图片；当前本地 NFO 解析也会丢弃没有 TMDb ID 的演员。

## 决策

将人物系统拆成三层：

1. 出演关系：保存姓名、角色和排序。没有稳定 ID 也必须能够展示。
2. Provider 身份：使用 `provider:id` 表示来源身份，例如 `tmdb:124`、`imdb:nm123` 或
   `douban:123`。
3. 规范人物：使用 Lux 自己的稳定 `personKey` 作为人物资源主键。多个已确认的 provider 身份可以
   指向同一个规范人物。

规范人物资源保存人物 NFO 和 Emby 风格的 `folder.<ext>` 图片。多个已确认的 provider 身份共用同一个
规范人物目录；目录已有头像时，后续 provider 不替换或新增头像。人物 NFO 按字段补充，已有非空字段不被
覆盖。没有稳定身份的演员只写入出演关系，不创建人物目录、不发起人物图片下载，并由 Web 显示占位图。

跨 provider 合并只接受明确的交叉身份信息或管理员确认；不根据姓名单独自动合并，以避免同名演员被错误合并。
旧版 provider 目录、旧 `people.json`、已有 `people/assets` 文件和旧图片路由保持兼容读取；新图片不再
写入 `people/assets`。

## 备选方案

### 继续使用 provider + id 作为人物主键

实现简单，但 TMDb、IMDb 和豆瓣会为同一人物创建重复目录和图片，无法满足跨来源复用。

### 仅按规范化姓名合并

可以减少目录数量，但同名演员会被错误合并，且姓名可能随语言或译名变化。风险不可接受。

### 新增人物数据库关系表

关系能力更强，但当前人物关系设计明确使用配置卷快照，新增数据库公共模型会扩大范围并增加 SQLite/PostgreSQL
迁移成本，因此暂不采用。

## 后果

- `people.json` 需要版本化并允许没有身份的出演关系。
- 详情 API 必须保持无图片演员可见，并对旧版 `id` 字段保持兼容。
- provider 身份索引、规范人物资源和图片资源需要原子写入与路径安全校验。
- 无法仅凭姓名保证所有 provider 都自动合并；管理员确认或来源交叉 ID 是最终合并依据。
