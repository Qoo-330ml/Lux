# ADR-011：弹幕采用 XML 旁车与 Dandanplay 兼容上游

## 状态

已接受，LUX-150 已实现，待真实客户端兼容性验证。

## 背景

Emby 标准字幕 API 描述的是 SRT/VTT/ASS 等字幕轨，并没有统一的弹幕协议。已知 Emby 弹幕插件和部分第三方客户端使用独立的 `/api/danmu/...` 约定，并以 Bilibili 标准 XML 作为交换格式。Lux 需要保留客户端选择，同时避免把弹幕伪装成普通字幕导致不支持弹幕协议的客户端行为不可预测。

用户指定的上游包括 Dandanplay 兼容 API，以及 `huangxd-/danmu_api`。后者的搜索、详情和评论接口兼容 Dandanplay，并提供便于后台匹配的 `/api/v2/match`。

## 决策

Lux 内置一个弹幕应用服务，不加载原始 Emby 插件二进制。它负责：

- 管理员配置一个经过校验的自定义 HTTP/HTTPS API 基地址；
- 使用 Dandanplay 兼容搜索、详情和 XML 弹幕接口，优先尝试 `danmu_api` 的 `match`；
- 把有效结果写为视频同名 `.xml` 旁车；
- 通过独立 Emby 兼容路由向有 ACL 权限的用户提供 XML；
- 以持久化后台任务处理匹配、重试、取消和重启恢复。

旁车是持久化事实，SQLite 只保存索引、provider ID、fingerprint 和任务状态，不保存整份 XML。读取端点优先提供已登记并通过路径约束的旁车。

## 替代方案

### 使用 Emby 标准字幕端点

拒绝：标准端点的媒体模型是字幕轨，不能表达弹幕评论、颜色、位置和时间轴，且不保证弹幕客户端会调用。

### 只把 XML 存进 SQLite

拒绝：会放大数据库和备份体积，也不能让支持本地旁车的客户端直接发现；媒体目录旁车更符合既有客户端习惯。

### 只实现 `danmu_api` 的专有接口

拒绝：会缩小兼容范围；Dandanplay 兼容接口是更稳定的公共边界，`match` 作为可选加速能力。

### 生成 ASS 旁车

暂不采用：用户确认首版只保证支持弹幕接口的客户端；ASS 属于另一类字幕渲染兼容，不在 LUX-150 范围。

## 后果

- 支持弹幕接口的第三方客户端可以通过 Lux 的 Emby 兼容路由读取统一 XML。
- 其他客户端是否显示 `.xml` 不属于 Lux 的兼容承诺。
- 媒体目录必须允许写入才能完成自动匹配；只读目录会得到明确失败状态。
- 上游 API 地址可能包含部署 token，配置、日志、审计和错误必须脱敏。
- 需要维护 Dandanplay 响应解析、XML 限制和真实客户端兼容性测试，但不需要把弹幕逻辑耦合进普通字幕模型。
