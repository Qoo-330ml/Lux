# ADR-033：全量扫描中的本地旁车流水线

## 状态

已接受

## 日期

2026-09-01

## 背景

全量扫描先把媒体文件建立为可用来源，再在扫描结束后统一读取本地 NFO 和图片。大媒体库中，后续文件夹即使
已经完成索引，也要等待前面的全部文件和统一后处理结束才能获得本地海报与元数据，首页反馈滞后。

需求只涉及媒体目录中已经存在的本地资源，不要求在线匹配、TMDb 请求或下载缺失图片。

## 决定

1. 全量扫描继续按现有持久化目录和文件工作队列推进。每次媒体源入库并提交对应扫描目标后，首页即可看到该条目。
2. 本地旁车处理使用独立的后台协调任务，轮询并消费已提交的 `ITEM` 元数据目标；它不取得文件扫描互斥锁，扫描
   worker 不等待旁车处理完成即可继续下一个文件夹。
3. 旁车目标继续使用 `scan_job_targets.metadata_state` 持久化。`PENDING` 表示首页可以显示等待状态；旁车 worker
   完成或失败后写入 `DONE`/`FAILED`，进程重启时仍可从数据库恢复 `PENDING` 目标。
4. 首页 Lux API 额外返回 `localMetadataPending`。该字段只描述本地旁车流水线，不与在线元数据候选的
   `metadataPending` 混用。
5. Web 在没有图片且 `localMetadataPending` 为真时显示占位图和等待图标；没有本地图片、旁车完成或旁车失败时
   显示普通占位图。
6. 全量扫描默认不再因为扫描完成而自动创建在线元数据补全任务。管理员显式执行的元数据匹配仍属于独立任务边界。

## 未采用的方案

### 扫描循环中直接等待当前文件夹的旁车处理

实现直观，但会使一个慢 NFO 或大图片阻塞下一个文件夹的发现和视频入库，违反全量扫描的持续推进要求。

### 旁车处理只使用内存队列

进程重启会丢失尚未消费的条目，首页也无法从稳定状态判断是否应显示等待图标。现有持久化扫描目标已经提供了
恢复所需的生命周期和幂等键，因此不增加另一套一次性队列。

### 旁车缺失时继续显示无限等待动画

目录没有海报是正常结果，不应让用户误以为仍在下载。worker 将目标标记为完成后，首页回到普通占位图。

## 后果

- 新条目可以先进入首页，随后在本地资源登记完成后通过首页失效事件获得海报和 NFO 字段。
- 扫描与旁车会竞争少量数据库和磁盘 I/O，因此旁车 worker 必须保持单个扫描任务一个有界协调器，并复用已有图片读取并发限制。
- `scan_job_targets` 在全量扫描结束前不能清理；扫描完成时需要等待旁车目标排空，保证任务恢复和重试语义不变。
- `localMetadataPending` 是 Lux Web 的新增字段；Emby 兼容 DTO 不暴露这个内部状态。

## 验证

- 扫描集成测试验证视频源入库后目标可被旁车 worker 消费，且不创建在线元数据任务。
- 首页 API 测试验证 `localMetadataPending` 的出现、清除和本地图片标签更新。
- Web 单测验证等待占位图、无图片完成态和本地海报显示。
- 运行 LUX-230 规定的 Rust/Web 检查，并记录本机架构。
