# ADR-027：元数据补全请求计划与图片资源队列

## 状态

已接受

## 日期

2026-08-26

## 背景

元数据任务已经在后台运行并具有有界 worker，但 `FILL_MISSING` 的执行路径仍可能为一个缺失字段的
条目请求完整的详情、图片、演职员、外部 ID 和预告片。图片写入还在条目 worker 内逐张串行执行；
图片 404 或临时错误没有持久化尝试状态，重复补全会再次访问同一个失效资源。人物详情请求虽然可选，
也不应继续占用元数据主任务的资源。

## 决策

1. 在应用层先将当前条目的未锁定字段、本地图片和媒体库图像策略转换为不可变的请求计划。请求计划
   只允许执行满足缺失条件的 capability；完整条目直接跳过在线刮削。
2. `metadata.bundle` 是一次完整候选展开的优先路径。旧插件不支持 bundle 时，应用层按计划并行调用
   必需的独立 capability；候选身份选择和 provider ID 规则仍遵守 ADR-024/025。
3. 图片尝试是持久化资源状态，而不是元数据候选状态。唯一键按条目、图片类型和候选身份键划分；
   不持久化外部凭据，日志只记录 provider、图片类型、状态和脱敏错误类别。
4. 图片资源使用独立的全局并发配额，并在条目内使用更小的并发上限。尝试状态在开始下载前原子领取，
   避免同一图片被并发任务重复下载；写入成功后才登记 `AVAILABLE`。
5. `UNAVAILABLE` 表示 provider 明确没有该图片或返回永久 404，不自动重试；`FAILED` 只表示可重试
   或未知失败，按有限指数退避计算 `next_retry_at`。手动刷新、provider 身份变化或图片策略变化可以
   显式重置状态。
6. 图片失败不回滚基础元数据。NFO、图片和人物资源继续分别原子写入，任务结果记录图片问题但保留
   已成功的字段和关系。
7. 进程全局元数据条目 worker 暂保持 8。是否提高到规格中曾出现的 16 路，必须由同一数据集、同一
   provider stub 和目标 NAS 的实测吞吐、p95、错误率和资源使用共同决定。

## 未采用的方案

### 直接把元数据 worker 提高到 16 或更高

这会同时放大插件 RPC、第三方 API、图片下载和 SQLite 写入压力；在请求扇出尚未减少前，吞吐可能不升反降，
并会使限流和失败重试更严重。先缩小每条目工作量，再根据基准调并发。

### 将所有图片缓存为永久外部 URL

外部图片 URL 可能过期、泄露部署信息或包含敏感查询参数，且无法表达 provider 变更和失败退避。Lux 继续
保存受保护的本地资源和有限状态，不把完整 URL写入日志或公共 API。

### 用内存 map 记录图片失败

进程重启后会丢失状态，导致 NAS 重启或定时任务再次产生请求风暴。图片尝试必须进入现有数据库 migration
体系，SQLite 和 PostgreSQL 保持同一语义。

## 后果

- `FILL_MISSING` 对已完整条目可以做到零上游请求；只有实际缺失内容才消耗 provider 配额。
- 图片资源的状态和任务状态分离，管理员需要在任务详情中看到“基础元数据成功、图片待重试/不可用”等可
  解释结果。
- 新增一个小型数据库表和两份 migration；查询必须带条目/图片类型索引，避免全表扫描。
- 图片并发受独立配额限制，短期峰值吞吐取决于上游、磁盘和 NAS，而不是单纯取决于元数据 worker 数量。

## 验证

- 固定 scraper stub 验证请求计划和请求计数。
- 图片 stub 覆盖成功、404、429、5xx、超时、损坏内容和并发下载。
- SQLite 空库 migration、PostgreSQL migration 文件校验和现有元数据/NFO/人物测试通过。
- release 模式记录阶段 p50/p95、请求数量、重试数、图片吞吐、前台请求 p95 和 `uname -m`。
