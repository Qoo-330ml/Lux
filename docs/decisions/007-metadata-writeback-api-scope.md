# ADR-007：管理员元数据写回 API 范围

- 状态：待项目所有者确认
- 日期：2026-08-03

## 背景

当前规格对管理员元数据写回 API 存在冲突：`docs/LUX-DEVELOPMENT.md` 的管理接口清单列出：

- `PATCH /api/v1/admin/items/{id}/metadata`
- `POST /api/v1/admin/items/{id}/metadata/refresh`

但 `docs/LUX-053-PLAN.md` 明确写明本阶段“不实现候选选择和 metadata PATCH”，`docs/LUX-054-PLAN.md` 又明确“不在本阶段开放管理员写回 API”；`docs/LUX-056-PLAN.md` 实际只定义并实现了候选选择端点：
`POST /api/v1/admin/items/{itemId}/identify/candidates/{candidateId}/select`。

这不是命名差异，而是会改变公共请求 DTO、字段锁定语义、审计事件和本地 NFO 写回边界的接口决策。

## 暂定决定

在项目所有者确认之前，不新增上述两个直接写回端点，也不从现有候选选择接口推断它们的请求体或刷新语义。当前唯一公开的管理员写回入口是候选选择流程，并继续遵守 `fillMissing` 与 `refreshUnlocked` 的字段保护规则。

## 备选方案

### 方案 A：直接实现主开发文档列出的两个端点

- 优点：管理接口清单看起来完整。
- 风险：无法确定 PATCH 的字段锁定、图片写回、provider ID 和审计语义；可能绕过 LUX-056 的原子写回流程。

### 方案 B：维持 LUX-053/LUX-054/LUX-056 的候选选择模型（当前暂定）

- 优点：所有写回都经过候选、字段保护、NFO/图片原子写入和状态更新流程。
- 风险：主开发文档的两个接口暂时缺失，需要项目所有者确认是否删除、延期或重新定义它们。

## 待确认问题

项目所有者需要选择以下一种处理方式：

1. 删除或延期主开发文档中的两个端点，以候选选择接口作为唯一写回 API；或
2. 补充两个端点的请求 DTO、字段锁定/刷新语义、图片处理、审计和错误契约，再单独实现并测试。

在确认前，不能把该冲突标记为已完成，也不能用 SenPlayer 兼容性问题替代这项规格决定。
