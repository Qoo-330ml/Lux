# ADR-034：关闭或重启时取消未完成后台作业

## 状态

已接受（LUX-233）。

## 日期

2026-09-02

## 背景

Lux 当前把扫描、媒体探测、章节检测、封面生成、弹幕匹配、元数据重新识别、Emby 导入和人物索引重建
持久化到数据库，并在服务启动时尝试领取遗留作业。这样可以保持游标和任务进度，但关闭期间的 worker
可能只完成部分外部副作用；重启后继续执行还会让用户误以为关闭动作只是暂停，并增加插件进程、文件写回
和旧 worker 迟到提交之间的生命周期复杂度。

产品决定是：关闭或重启应丢弃当前未完成的作业实例，不应因为数据库中仍有活动状态而自动继续。
任务历史仍需要保留，方便管理员知道发生了什么并主动重试。

## 决策

1. 数据库连接建立并完成迁移后，先在一个事务中把所有未完成的持久化后台作业标记为 `CANCELLED`，并
   记录稳定错误码 `SERVER_SHUTDOWN`。扫描任务包括 `COMPLETED + POSTPROCESSING`，因为其后处理仍未完成。
2. 正常优雅关闭时，在关闭数据库连接前再次执行相同的清理，覆盖关闭窗口内仍处于活动状态的作业。
3. 启动流程不再调用任何 `resume_*_jobs` 入口。管理员通过现有失败/取消重试入口主动重新排队；重试
   仍沿用各任务已有的幂等和游标规则。
4. 计划任务配置、插件安装状态、用户数据、媒体索引和已提交进度继续持久化，但计划任务不会把上一次
   被取消的作业实例当作自动恢复目标。Webhook 投递 outbox 是独立的持久化通知机制，继续按自己的
   投递重试策略处理，不纳入后台作业取消集合。

## 范围

统一清理以下作业表：

- `scan_jobs`
- `strm_probe_jobs`
- `chapter_detection_jobs`
- `library_cover_jobs`
- `danmaku_match_jobs`
- `metadata_reidentify_jobs`
- `emby_migration_jobs`
- `person_index_rebuild_jobs`

播放会话不是后台作业，不做重启恢复或取消语义改造。

## 备选方案

### 重启后继续领取 `PENDING/RUNNING`

拒绝。它与用户对关闭/重启的预期不符，并要求每类 worker 都正确处理旧 run token、外部副作用和取消竞态。

### 删除任务记录

拒绝。删除会丢失管理员可诊断的历史、错误码和进度，也会让关闭原因不可见。保留为 `CANCELLED` 可以复用
现有列表、详情和重试接口。

### 仅在正常 SIGTERM 时取消

拒绝。异常退出后数据库仍可能保留活动状态；下次启动必须先把遗留状态归档为取消，才能保证启动后绝不
自动继续旧作业。

## 后果

- 关闭或重启会放弃尚未提交的当前批次；已提交的数据库状态和文件写回不会回滚。
- 用户需要在管理员任务页主动点击重试，任务才会再次执行。
- 任务表会保留取消历史；现有生命周期清理可以在后续启动按既有策略清理其临时工作项。
- 计划任务仍可在下一次调度周期创建新的作业实例；这不是旧作业的恢复。

## 验证

- 数据库集成测试覆盖所有作业表、事务性取消、`SERVER_SHUTDOWN` 和活动查询为空。
- 扫描测试覆盖关闭清理后不自动继续，管理员重试仍可执行。
- 运行相关 Rust 测试、格式化、Clippy 和项目完成门禁，并记录本机 ARM 架构。
