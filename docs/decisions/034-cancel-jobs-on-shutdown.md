# ADR-034：关闭或重启时清理未完成后台作业

## 状态

已接受（LUX-233；元数据识别恢复规则由 LUX-572 修订）。

## 日期

2026-09-02

## 背景

Lux 当前把扫描、媒体探测、章节检测、封面生成、弹幕匹配、元数据重新识别、Emby 导入和人物索引重建
持久化到数据库，并在服务启动时尝试领取遗留作业。这样可以保持游标和任务进度，但关闭期间的 worker
可能只完成部分外部副作用；重启后继续执行还会让用户误以为关闭动作只是暂停，并增加插件进程、文件写回
和旧 worker 迟到提交之间的生命周期复杂度。

产品决定是：关闭或重启时先将活动作业标记为 `CANCELLED/SERVER_SHUTDOWN`，保留历史记录。元数据识别任务
在下次启动时恢复原任务 ID 中未完成的子项；其他作业继续等待管理员主动重试或后续计划任务。

## 决策

1. 数据库连接建立并完成迁移后，先在一个事务中把所有未完成的持久化后台作业标记为 `CANCELLED`，并
   记录稳定错误码 `SERVER_SHUTDOWN`。扫描任务包括 `COMPLETED + POSTPROCESSING`，因为其后处理仍未完成。
2. 正常优雅关闭时，在关闭数据库连接前再次执行相同的清理，覆盖关闭窗口内仍处于活动状态的作业。
3. 元数据识别任务是唯一自动恢复的作业类型：启动时仅恢复 `SERVER_SHUTDOWN` 任务中未完成的子项，完成项不重跑，
   用户主动取消的任务不恢复。`FILL_MISSING` 还必须确认媒体库启用且仍选中刮削器；恢复仍沿用原任务 ID 和有界
   dispatcher。其他作业通过现有失败/取消重试入口主动重新排队，仍沿用各任务已有的幂等和游标规则。
4. 计划任务配置、插件安装状态、用户数据、媒体索引和已提交进度继续持久化；除元数据识别外，计划任务不会把
   上一次被取消的作业实例当作自动恢复目标。Webhook 投递 outbox 是独立的持久化通知机制，继续按自己的
   投递重试策略处理，不纳入后台作业取消集合。

## 范围

统一清理以下作业表：

- `scan_jobs`
- `strm_probe_jobs`
- `chapter_detection_jobs`
- `library_cover_jobs`
- `danmaku_match_jobs`
- `metadata_reidentify_jobs`
- `emby_migration_jobs`
- `person_index_rebuild_jobs`

播放会话不是后台作业，不做重启恢复或取消语义改造。

## 备选方案

### 重启后恢复所有后台作业

拒绝。只恢复元数据识别任务；全面恢复会要求每类 worker 都正确处理旧 run token、外部副作用和取消竞态。

### 删除任务记录

拒绝。删除会丢失管理员可诊断的历史、错误码和进度，也会让关闭原因不可见。保留为 `CANCELLED` 可以复用
现有列表、详情和重试接口。

### 仅在正常 SIGTERM 时取消

拒绝。异常退出后数据库仍可能保留活动状态；下次启动必须先把遗留状态归档为取消，才能保证启动后绝不
自动继续旧作业。

## 后果

- 关闭或重启会放弃尚未提交的当前批次；已提交的数据库状态和文件写回不会回滚。
- 用户仍需在管理员任务页主动重试除元数据识别以外的取消任务；元数据识别的未完成条目会在服务启动后自动继续。
- 任务表会保留取消历史；现有生命周期清理可以在后续启动按既有策略清理其临时工作项。
- 计划任务仍可在下一次调度周期创建新的作业实例；这不是旧作业的恢复。

## 验证

- 数据库集成测试覆盖所有作业表、事务性取消、`SERVER_SHUTDOWN` 和活动查询为空。
- 扫描测试覆盖关闭清理后不自动继续，管理员重试仍可执行。
- 运行相关 Rust 测试、格式化、Clippy 和项目完成门禁，并记录本机 ARM 架构。

## 修订（2026-10-14）：重启后补全在线刮削

用户反馈刮削经常"做到一半停下"：关闭或重启会取消 `FILL_MISSING` 作业，而管理员通常不会去手动重试。

当时的决定是不恢复旧任务实例，而为最近被取消的 `FILL_MISSING` 媒体库新建整库任务。该例外由 LUX-572
取代：恢复原任务 ID 和未完成子项，避免同库整库重扫及历史任务重复堆积。

同时修正两个会让作业"静默停下"的缺陷：领取条目失败时作业不再被记为 `COMPLETED`（改为 `FAILED` /
`QUEUE_INCOMPLETE`，保留 `PENDING` 条目以便重试）；无法派发的作业记为 `FAILED` / `DISPATCH_FAILED`，
不再长期停留在 `QUEUED`（关闭窗口内的 `ShuttingDown` 除外，由关闭清理统一处理）。

## 修订（2026-10-17）：恢复元数据识别任务

项目所有者要求重启后继续未完成识别，而不是只重建一条新的整库补缺任务。LUX-572 将 `SERVER_SHUTDOWN`
作为可恢复原因：下一次启动原子地把原任务恢复为 `QUEUED`，仅重排未完成子项；已完成项不重跑，管理员主动
取消不恢复。`FILL_MISSING` 只在库仍启用且已选择刮削器时恢复。其他后台作业仍维持 LUX-233 的取消语义。
