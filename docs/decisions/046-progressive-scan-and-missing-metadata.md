# ADR-046：渐进扫描、本地优先处理与独立在线补缺

## 状态

已接受；运行时实现按阶段 23 分任务交付。

## 日期

2026-09-28

## 背景

LUX-230 与 ADR-043/LUX-264 为全量扫描选择了稳定的旧首页快照，并在全量索引和 target-ready 后启动本地 NFO/图片处理。该顺序保护了整库删除和索引完成事件，但当列表已展示大量资源时，本地海报登记仍可能晚于扫描入库；全量扫描也没有把成功本地检查确认的缺失项提交到独立在线补缺队列。

产品要求是在扫描继续遍历后续资源的同时，逐批展示已提交资源、读取本地 NFO/图片，并将本地检查确认的缺失交给独立 FILL_MISSING 任务。扫描路径本身仍不得执行网络刮削。

## 决策

### 新旧工作流隔离

- 新建扫描使用 `workflow_version=3`、`discovery_format_version=3` 和 Lite frontier。已有 workflow 1/2 以及已持久化任务仍由原执行器恢复，不能套用新事件、队列或完成状态解释。
- `workflow_version=3` 的正向索引批次在其事务成功提交后即可通过有界、分页的目录查询读取。Lux Web 按合并后的失效通知刷新当前目录和首页投影。
- 尚未遍历完成的根路径仍不得导致媒体删除。只有根路径完整且身份一致、缺失在文件系统二次检查中成立、基线 ID/fingerprint CAS 成功时才可应用 REMOVE。旧媒体在安全删除提交前继续可见。
- `ScanCompleted` 与 `JOB_COMPLETED` 继续表示 Manifest 索引及缺失确认完成。`POSTPROCESSING`/`IDLE` 继续描述扫描侧本地后处理；在线 FILL_MISSING 有独立任务状态，不进入扫描进度。

### 本地旁车工作

- 正向索引提交必须在同一事务中登记有界、持久化、幂等的本地 NFO/图片处理意向。事务回滚时不得留下队列记录，队列记录不得指向未提交媒体。
- 新本地 worker 可消费这些意向，而无需等待整库 discovery 或 v3 的最终 SOURCE/ITEM target-ready barrier。扫描继续处理后续目录，不等待本地读取。
- `scan_job_targets` 与 target-ready barrier 继续保护需要完整 target 集合的 probe、缩略图和旧 workflow worker。新早期队列不得削弱旧屏障的正确性。
- NFO/图片状态按可独立判断的能力持久化。海报可以先于慢 NFO 显示；只有对应能力的本地检查成功完成后才能确认该能力缺失。读取失败、root 不可用和 PENDING/RUNNING 均是可重试状态，不得当作缺失。
- 每项工作应用前检查 source/root 身份和输入版本。取消、重试、崩溃恢复和并发增量扫描不得让旧结果覆盖较新的本地数据或元数据编辑。

### 独立在线补缺

- 扫描和本地旁车不得直接调用 provider 或下载缺失图片。只有本地检查确认的缺失能力才可以生成在线调度意向；写入缺失状态与调度意向必须原子化。
- 新建媒体库的全量/手动扫描自动补缺默认开启；既有媒体库新增该设置时，其升级初值复制原 `realtime_metadata_auto_match_enabled`，从而保留管理员明确关闭自动匹配的决定。实时增量仍沿用原开关。管理员可分别关闭扫描触发的自动补缺。
- `MetadataRequestPlan` 决定真实缺失和可请求能力；本地图片/继承图片、策略关闭、字段锁定、provider 能力与冷却均参与判断。HOMEVIDEOS 与 VIDEO 不进行在线自动识别。
- dispatcher 将意向合并到现有定向 `FILL_MISSING` 入口，遵守每项任务最多 100 个条目的边界和进程级 provider 并发额度。活跃项去重；worker 领取和写入前重新判定当前缺失，只填空值，不覆盖本地或锁定数据。
- 在线任务与扫描具有独立取消、失败、重试和统计。取消扫描不撤销已提交的在线工作；在线失败不改变索引成功状态。migration 不访问 provider、不扫描文件系统，也不为历史媒体库批量补建刮削任务。

#### 自动补缺的持久队列与显式提交

- 自动扫描入口先在完整性事务中持久化 `QUEUED` FILL_MISSING job，再向所属 library dispatcher 发送合并的唤醒信号；完整性 worker 不等待内存队列空位或在线 job 完成。
- 自动 job 的持久化状态是待处理工作的来源。每库保持一个有界 dispatcher，按创建顺序分页领取可自动派发的 job；dispatcher 空闲时读取已持久化的工作，进程重启后也能继续处理。不得为每个 job 创建独立 Tokio task，也不得把所有待处理 ID 堆进无界内存队列。
- 自动补缺与管理员/计划任务显式提交使用持久化来源标记区分。dispatcher 仅主动拉取自动来源 job；显式入口继续等待其有界 dispatcher 容量，并保留已有的完成 receiver、取消、去重和每库串行执行语义。自动工作不能改写显式任务的排队合同。
- 自动来源 job 之间按既有规则合并和去重，单 job 最多 100 个条目。自动工作不得并入显式来源 job；显式重试继续按显式入口调度。
- `ScanCompleted`、`JOB_COMPLETED`、扫描 `POSTPROCESSING`/`IDLE`、Webhook 与 Emby 合同不因 dispatcher 唤醒或在线队列排空时点改变。

### 前端与兼容性

- Lux Web 只刷新当前已加载的分页/首页数据，按批次合并通知；不逐条推送整库，不要求浏览器确认绘制后 worker 才能运行。新 image tag 使已打开卡片读取新图，屏幕外图片继续懒加载。
- Emby 路由、DTO 和图片标签合同不变。`ScanCompleted`/`JOB_COMPLETED` 继续表示索引完成，不等待本地队列或在线队列。
- `localMetadataPending` 继续可用，并扩展为能正确反映早期本地队列；等待状态在完成、失败或取消后必须结束。

### 性能约束

- 索引 writer、扫描互斥锁、Manifest CAS、root 覆盖安全和分页上限保持原合同。
- 本地读盘、扫描、数据库写入和在线网络分别限并发；前台负载升高时降低后台压力。目录枚举和文件名索引应跨同一父目录的有界批次复用。
- 不能假设新增工作对索引耗时零影响。阶段 23 使用相同 fixture 和构建配置比较 SQLite/PostgreSQL，分别记录索引完成、首批可见、首张本地海报、队列处理与前台 p95。稳定索引或前台 p95 回退超过 5% 时调整并发/批次后重测；本机 ARM 结果不外推 NAS/x86。

## 考虑过的方案

### 等待全量 target-ready 后开始本地处理

这保持现有顺序简单，但会令早已提交并已展示的资源继续等待后续全库遍历。本 ADR 为 workflow 3 增加事务内的早期本地工作意向，既有 targets-ready 屏障继续服务于其他后处理。

### 由前端首次请求图片时才处理本地旁车或触发在线刮削

页面 GET 可能被刷新、预取、爬虫或重复请求放大，也会导致未浏览目录永远没有本地海报。扫描提交本地工作与用户是否打开页面无关；在线补缺由确认缺失的本地结果和管理员策略触发。后续如需可见项优先级，应使用有鉴权、有界、去重的显式意向。

### 在扫描 worker 中直接请求 provider

网络限流或 provider 故障会占住扫描资源，也无法与扫描完成、重试和用户取消独立管理，因此不采用。

## 后果与验证

- SQLite 和 PostgreSQL 需要兼容的追加式 schema 与存储接口；旧任务由 workflow 版本保持旧语义。
- 扫描任务的索引完成时间和所有后台本地/在线处理耗时分开呈现。
- 方案与正式规格同步于 `docs/LUX-DEVELOPMENT.md`，运行时代码及性能结果需通过阶段 23 的独立 LUX 任务交付后再记录为已实现。
- 自动与显式来源的区分需要追加式 SQLite/PostgreSQL migration；旧记录以显式来源默认值升级，不推断其历史触发来源。自动完整性写入、跨后端升级、超过 32 个 job 的慢 provider 排空、取消、关闭和恢复均需回归。
- 持久化自动队列修复与刮削吞吐/可见性是独立 LUX 任务；阶段 23 的既有性能门保持开放，直到其完整 A/B 条件另行满足。
