# ADR-039：按任务类型聚合执行计划

## Status

Accepted

## Date

2026-09-07

## Context

当前计划任务以 `(owner_type, owner_id, task_type)` 作为唯一注册项。媒体库创建时会为每个库注册
全量校验和元数据任务；当多个任务类型作用于多个媒体库时，管理员需要在列表中维护大量外观相同的
计划。与此同时，媒体库并不能因为计划配置聚合就同时执行：文件扫描共享全局扫描锁，实时增量扫描
还需要优先让出资源。

需要同时解决配置数量、错峰计划和实际执行隔离三个问题。

## Decision

引入三层模型：

1. 任务类型由系统或插件注册，只描述“做什么”。
2. 执行计划由管理员维护，描述“哪些媒体库在什么时候做”，同一任务类型允许多个计划。
3. 运行任务仍按媒体库拆分，负责进度、取消、重试和失败状态。

执行计划到点后创建批次语义的调度请求，但不改变已有每库运行任务。计划之间共享资源调度器；全量
扫描默认并发 1，实时增量扫描优先，重复计划和活动媒体库任务通过现有去重规则合并。

同一任务类型下，一个媒体库只能归属一个计划。新媒体库加入匹配的默认计划；需要错峰的管理员创建
自定义计划并将媒体库移动过去。

为降低迁移风险，保留 `scheduled_task_configs` 作为有效配置镜像和旧 API 兼容层。新计划的更新与
镜像同步在同一事务内完成；旧 API 修改单库计划时自动创建或选择单库覆盖计划。

## Alternatives Considered

### 只在前端折叠现有注册项

实现成本低，但仍需逐库修改计划，也不能表达多个媒体库计划组，无法解决配置维护成本，拒绝。

### 一个全局任务直接负责所有媒体库

可以减少注册项，但会让进度、取消和失败边界变粗；一个大库失败可能影响其他库，也难以支持错峰，拒绝。

### 完全删除旧的媒体库级配置

模型更干净，但会破坏现有 API、插件同步和已部署数据库的行为，迁移风险过高，拒绝。

## Consequences

- 管理页面主要展示任务类型和执行计划，10 个媒体库通常只需维护少量计划。
- 不同计划可以使用不同 Cron；统一计划不会造成 10 个扫描同时执行。
- 数据库新增计划和关联表，并需要从旧配置按有效配置分组迁移。
- 旧配置在短期内重复保存计划字段，需要严格保证事务内同步。
- 全局插件任务仍由插件配置管理媒体库选择，暂不拆成多个全局插件计划。
