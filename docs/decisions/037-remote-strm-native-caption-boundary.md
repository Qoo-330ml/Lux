# ADR-037：远程 STRM 保持原生媒体播放，字幕只使用浏览器原生轨道

## 状态

已被 ADR-038 取代。本文记录 native-only 中间方案以及它为何无法满足“远程内嵌字幕可用”的需求。

## 日期

2026-09-07

## 背景

字幕功能改动曾把远程 HTTP(S) STRM 的 Matroska 资源交给 JavaScript Range/MSE 管线。该管线要求网页脚本读取远程媒体字节，
因此会额外依赖 Range、CORS、重定向、索引和 MSE codec。任何一个条件失败，原本可以由原生 `<video>` 播放的音视频也会变成
“播放器引擎失败”。这违反了字幕能力不应改变既有 Direct Play 行为的边界。

浏览器原生媒体管线可以解封装并播放音频、视频，但不保证把 Matroska 内嵌文本字幕暴露给页面的 `video.textTracks`。脚本不能
凭借 ffprobe 或 API 的字幕列表，强行创建浏览器没有提供的原生字幕轨道。

## 决定

1. 远程 HTTP(S) STRM 始终使用原生 `<video>` 播放当前播放计划的媒体 URL；优先使用已有 `proxyUrl`，仅在它失败时沿用既有的
   签名 Lux Direct URL 回退。无论字幕是否存在，都不启动 `ClientMkvEngine`、Worker、Range、MSE 或字幕专用连接。
2. 远程内嵌文本字幕只有在当前 `<video>` 实例实际暴露为 `TextTrack` 时才可选。选择只切换该轨道的 `mode`，不改变媒体 URL、
   播放会话、tier、进度、心跳、停止请求或请求头。
3. 如果浏览器没有暴露远程字幕，字幕选项显示“浏览器未暴露远程内嵌字幕”，但音视频继续播放；不得通过远程字幕端点、服务端
   抽取、Range Relay、HLS、ffmpeg、预抽取、落盘或外挂字幕生成来兜底。
4. 本地 Matroska 的既有客户端 fallback 和 source-scoped 字幕 overlay 保持不变。它们只适用于本地媒体，不能被远程 STRM 复用。
5. 远程字幕轨道和媒体流的对应关系以运行时 `TextTrack` 为事实来源；API/ffprobe 的轨道信息只用于标签、语言、default/forced 等
   提示，不能把不可见轨道标为可用。

## 备选方案

### 远程字幕显式选择后进入 Range/MSE 单管线

拒绝。它会让一个可播放的远程媒体依赖额外的 CORS、Range、索引和 MSE 条件，并再次引入“字幕选择导致视频失败”的回归。

### Lux 服务端读取并抽取远程字幕

拒绝。会改变远程资源的访问主体、User-Agent、Cookie、短期令牌和单连接语义，扩大 SSRF、带宽和隐私风险，也违反 STRM
Direct Play 边界。

### 将 Matroska 字幕转换为外挂字幕

拒绝。用户明确要求不预先抽取、不落盘、不生成外挂字幕；同时会引入额外请求和生命周期，不能解决远程资源授权问题。

## 后果

- 恢复字幕改动前远程 STRM 的音视频兼容性：远程媒体始终走原生播放路径。
- 远程内嵌字幕的可用性取决于浏览器和上游媒体是否暴露 `TextTrack`，因此不承诺跨浏览器、跨 CDN 的 Matroska 内嵌字幕可见性。
- 字幕不可用只影响字幕菜单，不得显示播放器引擎失败，也不得触发第二条媒体连接。
- 如果未来要跨浏览器保证远程内嵌字幕，必须另立完整客户端媒体管线 ADR，并证明它不会改变无字幕播放的默认路径；不能作为普通
  fallback 混入当前播放器。

## 验证

- Web 测试确认远程 Matroska 不调用 `shouldUseClientMkv`，无原生轨时字幕选项不可用且原生视频 URL 保持不变。
- Web 测试确认实际发现 `TextTrack` 后可选字幕只使用 `native-inband`，不生成 `/subtitles/...` URL。
- 生产构建和全量 Web 测试通过；真实浏览器部署后应检查没有 Range/MSE/字幕专用请求，且原生媒体请求仍按既有代理/签名回退顺序。
